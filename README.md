# ParserBank

Телеграм-бот, который читает счёт в интернет-банке ВТБ и присылает поступления.

- `/balance` — остатки по счетам и картам
- `/last` — последние операции (по умолчанию 5)
- `/last` — история операций, листается кнопками по 5 штук
- `/backfill [месяцев]` — догрузить историю за прошлые месяцы
- `/status` — всё ли в порядке
- `/mirrors` — какие зеркала банка живы
- `/login` — вернуть окно браузера на страницу банка
- уведомление в личку при каждом зачислении

Управление продублировано инлайн-кнопками: баланс, история со стрелками
листания, статус.

**Про глубину истории.** Обычный опрос смотрит последний месяц — это то окно,
которое запрашивает сам сайт. Всё, что старше, лежит за пределами этого
периода, и его надо запрашивать отдельными окнами: этим занимается
`/backfill`. Окна берутся по одному с паузами — пачка запросов подряд ровно то,
на что реагирует антифрод.

Только чтение. Переводы бот не делает — [почему](#почему-бот-не-делает-переводы).

## Про сертификаты Минцифры

Их **не нужно** ставить. Зеркала ВТБ работают на обычном Let's Encrypt —
проверено `openssl s_client`:

| Хост | Издатель | Проверка цепочки |
|---|---|---|
| `online.sbpvtb.ru` | Let's Encrypt YE1 | `0 (ok)` |
| `sso-ib.sbpvtb.ru` | Let's Encrypt YE1 | `0 (ok)` |
| `async-online3.sbpvtb.ru` | Let's Encrypt YE1 | `0 (ok)` |
| `online.vtb.ru` | Минцифры РФ | `19 (self-signed in chain)` |

Минцифровский корень нужен только основному домену `online.vtb.ru`. На зеркале
стандартный Go-клиент и Chromium подключаются без единой настройки.

Если однажды понадобится — сертификат всё равно **не обязательно ставить в
систему**. Его кладут рядом с проектом и скармливают только своему процессу:

```bash
NODE_EXTRA_CA_CERTS=./russian_trusted_root_ca.pem go run ./cmd/bot
```

## Как это работает

Личный кабинет — SPA: из 344 КБ главной страницы 308 КБ занимает inline-JS, а
разметки почти нет. Балансы приезжают JSON'ом в ручки `/services/…`, поэтому
парсить HTML бессмысленно — там нечего парсить.

Обычный HTTP-клиент банк тоже не пропустит: на входе SSO с OTP, Yandex
SmartCaptcha и антифрод F6 (экс-Group-IB), снимающий отпечаток устройства.

Поэтому схема такая:

```
Chromium с постоянным профилем (Playwright)
        │  профиль хранит куки и отпечаток устройства
        ▼
APIRequestContext ──► /services/… ──► JSON
        │
        ▼
   поллер ──► SQLite (последние N операций)
        │
        ▼
   Telegram
```

Запросы уходят через `APIRequestContext` браузера, а не через `net/http`: так
они наследуют куки живого профиля и тот же TLS-стек, что и запросы самой
страницы.

## Установка

Нужны Go 1.24+, Node.js и установленный Google Chrome.

```bash
cp .env.example .env
./scripts/install-driver.sh
```

Заполните в `.env` как минимум `TG_BOT_TOKEN` (от [@BotFather](https://t.me/BotFather))
и `TG_OWNER_ID` (ваш ID, узнать у [@userinfobot](https://t.me/userinfobot)).

Проверить, что окружение готово, — не заходя в банк:

```bash
make doctor
```

Он покажет чеклист: конфиг, драйвер, запуск браузера, какие зеркала резолвятся,
есть ли `endpoints.json`.

### Почему отдельный скрипт для драйвера

playwright-go качает драйвер с `playwright.azureedge.net`, который Microsoft
выключил. Зеркало `cdn.playwright.dev` редиректит на
`playwright.download.prss.microsoft.com`, а тот отвечает
`400 GatewayExceptionResponse` — на любые заголовки и на любую версию.

Ровно тот же пакет лежит в npm-реестре и качается оттуда нормально, поэтому
`install-driver.sh` берёт `playwright-core` из npm и раскладывает в том виде,
который ждёт playwright-go: `package/cli.js` плюс симлинк на системный `node`.

Браузер не качается вообще — используется установленный Chrome через
`BROWSER_CHANNEL=chrome`. Для антифрода это даже лучше: настоящий Chrome
выглядит естественнее сборки Chromium.

### Если Chrome не запускается на macOS

macOS может показать «Приложение заблокировано при попытке внести изменения
в приложения на Вашем Mac». Выдайте разрешение тому, откуда запускаете:
**Системные настройки → Конфиденциальность и безопасность → Управление
приложениями**. Или запустите из `Terminal.app` вместо встроенного терминала
IDE — у него свои разрешения.

`make doctor` подскажет это сам, если запуск браузера упадёт.

### Шаг 1. Discovery — найти ручки банка

Внутреннее API ВТБ нигде не документировано и меняется без предупреждения.
Адреса ручек и названия полей снимаются с живого сайта один раз:

```bash
make record
```

Откроется окно браузера. Дальше:

1. Войдите в кабинет руками
2. Откройте главную со счетами
3. Откройте историю операций и пролистайте её
4. Дождитесь строчки `✓ нашёл и счета, и операции` и нажмите `Ctrl+C`

`endpoints.json` соберётся сам. Разбирать дампы руками не нужно: анализатор
находит нужные массивы по форме данных (дата + сумма + код валюты — это
операции; остаток + валюта без дат — счета), определяет пути к полям и
подставляет их в конфиг. В консоль печатается отчёт, что именно он выбрал.

Перепройти разбор по уже снятым дампам, не заходя в банк:

```bash
make map
```

`make report` — то же, но только показать отчёт, ничего не записывая.
Существующий `endpoints.json` не затирается: предложение ляжет рядом,
в `endpoints.suggested.json`.

**Про токен.** Recorder сопоставляет значение `Authorization` с содержимым
`localStorage`, `sessionStorage` и кук и записывает, из какого ключа фронт
берёт токен. Сам токен на диск не попадает — только адрес ключа; свежее
значение клиент берёт с живой страницы при каждом запросе.

Дампы содержат **ваши финансовые данные** (заголовки авторизации вырезаны, тела
ответов — нет), поэтому каталог `data/` целиком в `.gitignore`.

### Шаг 2. Проверить endpoints.json

Анализатор работает эвристиками, поэтому результат стоит пробежать глазами.
Формат файла:

| Поле | Что это |
|---|---|
| `url`, `method` | адрес и метод из дампа |
| `headers` | заголовки; `{{token}}` подставится из `token` |
| `body` | тело запроса (для POST) |
| `token` | откуда взять токен: `storage` = `local` / `session` / `cookie`, `key` — ключ, `path` — gjson-путь внутри значения, если там JSON |
| `params` | параметры запроса, пересчитываемые на каждый вызов: `offset` вида `-32d`/`0d` и `layout` — формат даты в стиле Go |
| `list` | [gjson](https://github.com/tidwall/gjson)-путь до массива, напр. `data.items`. Пусто = массив в корне. Суффикс `.@values` разворачивает объект-справочник в массив |
| `fields` | логическое имя → gjson-путь внутри элемента |
| `time_layout` | формат даты в стиле Go, напр. `02.01.2006 15:04`. Пусто = автоопределение |
| `in_values` | значения `direction`, означающие зачисление |

Если поля `direction` в ответе нет — уберите его из `fields`, направление
определится по знаку суммы. Направление может быть и булевым: ВТБ кладёт в
каждую операцию `debet: true/false`, и тогда `in_values` будет `["false"]` —
зачисление там, где флаг списания снят.

### Что оказалось нетривиальным в ответах ВТБ

Всё это анализатор разбирает сам, но знать полезно — если банк поменяет API,
чинить придётся здесь же:

- **Счета и карты приезжают не массивом**, а объектом, где ключ — идентификатор
  продукта: `"accounts": { "0BB2AA02…": {…} }`. В `list` это выражается
  суффиксом `.@values`.
- **У счёта есть даты** (`openDate`, `expireDate`), и по «есть дата → это
  операции» их не отличить. Разделение идёт по смыслу имени.
- **Рядом с суммой лежит комиссия** (`feeAmount.sum` возле
  `operationAmount.sum`) — берётся основная.
- **Идентификатор нужен уникальный.** В операции есть `accountProductId`,
  одинаковый у всех записей: приняв его за ID, бот схлопнул бы всю историю
  в одну строку. Кандидат проверяется на различие значений.
- **История запрашивается за период.** Диапазон дат в адресе обязан
  пересчитываться от текущего момента, иначе бот навсегда застрянет на том
  интервале, который был в момент записи, и не увидит ни одного нового
  поступления. Этим занимается `params`.
- **Записаться может любая страница истории.** Пролистывая её, фронт
  запрашивает всё более старые периоды, и в дамп попадает, например, окно
  «май–июнь». Поэтому окно не сохраняется как есть, а сдвигается: самая поздняя
  из найденных дат становится «сейчас», длительность периода сохраняется. Какая
  страница попалась — перестаёт иметь значение.

Схема вынесена в JSON намеренно: когда банк поменяет API, чинится это правкой
одного файла, без пересборки. Образец с комментариями — в
[endpoints.example.json](endpoints.example.json).

### Шаг 3. Запуск

```bash
make bot
```

Первый проход сохраняет историю молча — иначе прилетело бы 10 уведомлений
обо всём подряд. Уведомления начинаются со второго прохода.

## Зеркала

ВТБ раздаёт кабинет с пула доменов и меняет их по мере блокировок. Список
кандидатов зашит в `internal/bank/mirrors.go` — он вытащен из CSP самого сайта.

`BANK_HOST=auto` включает автоподбор. Ищет он в два шага, и порядок тут не
косметический:

1. **DNS.** Отсеивает мёртвые домены, не отправив банку ни одного запроса.
2. **Проба браузером.** Выживших проверяет `APIRequestContext` живого
   Chromium, с паузой в 2 секунды между кандидатами.

Второй шаг именно браузером по измеренной причине: edge банка отдаёт
`302 Security Redirect` не-браузерным клиентам уже через несколько запросов, а
дальше просто рвёт соединение. Проба через `http.Client` отработает ровно один
раз и приведёт к бану IP — то есть сломает ровно то, что чинит.

Полный перебор запускается только когда текущее зеркало не ответило трижды
подряд, с кулдауном 10 минут.

**Важно:** куки привязаны к домену. После переезда на другое зеркало сессия не
переезжает — бот попросит `/login` заново.

Замер на 2026-08-13: из девяти доменов CSP резолвились три —
`online.sbpvtb.ru`, `online.vtbsbp.ru`, `online.vneshtbank.ru`. Остальные
заведены про запас.

## Локально и на VPS

Переключается через `RUNTIME` в `.env`.

**`RUNTIME=local`** — макбук. Окно браузера видно, вход руками, ничего больше
не нужно.

**`RUNTIME=vps`** — сервер. Кроме дефолтов запуска, этот режим включает
экономию памяти в Chromium: один процесс рендерера, выключенные расширения,
фоновые сервисы и синхронизация. Отпечаток браузера при этом не трогается —
подменять user-agent или отключать картинки ради памяти дороже, чем эту память
докупить.

Флаг `--disable-dev-shm-usage` включён **всегда**, а не только на сервере: на
VPS и в контейнерах `/dev/shm` обычно 64 МБ, кабинет банка их выбирает, и
вкладка падает с «Target crashed» — вместе с сессией, которую потом
восстанавливать руками.

Реальный расход (измерено на macOS, Linux экономнее — там RSS не считает общую
память Chromium заново в каждом процессе):

| Процесс | RSS |
|---|---|
| Chromium (12 процессов) | ~1,1 ГБ (на Linux ждите 500–800 МБ) |
| Playwright-драйвер (node) | 26 МБ |
| Сам бот (Go) | 13 МБ |

Берите **2 ГБ RAM**. На 1 ГБ со swap OOM-killer рано или поздно прибьёт
Chromium — а вместе с ним сессию. Диск: профиль растёт за счёт кеша (уже сотни
мегабайт), закладывайте 10–20 ГБ.

Тут есть нюанс: `HEADLESS=true` антифрод замечает,
поэтому правильнее headful под виртуальным дисплеем:

```bash
sudo apt install xvfb x11vnc
xvfb-run -a --server-args="-screen 0 1440x900x24" ./bin/bot-linux
```

Для первого входа руками пробросьте VNC на локальную машину:

```bash
x11vnc -display :99 -localhost -rfbport 5900 &
ssh -L 5900:localhost:5900 user@vps
```

Альтернатива проще: залогиниться на макбуке и скопировать готовый профиль:

```bash
rsync -a data/profile/ user@vps:/opt/parserbank/data/profile/
```

Сборка бинарника под сервер:

```bash
make build-linux
```

`CGO_ENABLED=0` работает, потому что SQLite-драйвер (`modernc.org/sqlite`)
написан на чистом Go.

**Про IP.** Заграничный VPS почти гарантированно даст постоянные требования
переподтвердить вход, а то и блокировку. Российский домашний IP или VPS в РФ —
сильно спокойнее.

## Вход живёт ровно столько, сколько процесс

Это главное ограничение, и обойти его не удалось.

Токен ВТБ лежит в `sessionStorage`, а он привязан к вкладке и исчезает вместе
с окном браузера. Куки сохраняются, но сессию не поднимают: после перезапуска
браузера SPA не кладёт токен обратно даже через 45 секунд ожидания.

Перенос `sessionStorage` на диск был написан и **проверен — не работает**.
Снимок восстанавливается в страницу до загрузки SPA, но сервер такой токен не
принимает: сайт всё равно уходит на `/login`. Код удалён — хранить банковские
токены в файле ради нулевого эффекта незачем.

Что это значит на практике:

- бот держит **одно** окно браузера всё время своей жизни;
- при старте это окно открывается на странице банка — просто войдите в нём,
  когда удобно; бот проверяет страницу раз в три секунды и сам заметит вход;
- любой перезапуск процесса — новый вход руками.

Команду отправлять не нужно: пока вход не сделан, бот не шлёт в банк ни одного
запроса, а как только увидит токен на странице — напишет «✅ Вижу вход».
`/login` существует только чтобы вернуть окно на страницу банка, если оно
куда-то ушло.

Отсюда важное для VPS: `systemd` с `Restart=always` тут **не помогает**. После
автоперезапуска бот поднимется, но в банк ходить не сможет и будет ждать, пока
вы зайдёте руками. Автоперезапуск лечит падение процесса, а не потерю входа.

**Сессию держит именно опрос.** ВТБ разлогинивает после 3–5 минут бездействия,
а единственная активность, которую видит банк, — запросы бота. При
`POLL_INTERVAL=60s` таймаут не наступает никогда; поставить «поэкономнее», 5
минут, значит собственноручно себя разлогинивать. Поэтому интервал больше `2m`
отвергается на старте: это не вежливость к банку, а условие работоспособности.

Что тогда убивает сессию: абсолютный лимит на стороне банка, антифрод или
перезапуск процесса. Поэтому `/status` показывает, сколько уже держится текущий вход и
сколько живёт процесс, а в лог при потере входа пишется, сколько сессия
прожила, — за пару недель наберётся своя статистика вместо чужих оценок.

Для постоянно работающего бота это терпимо: логиниться приходится после
обновления, падения или перезагрузки машины, а не каждый день. Проверить
состояние можно в любой момент:

```bash
make doctor
```

Строка «вход из профиля» скажет, жива сессия или нужен `/login`.

Отдельно: **не закрывайте окно браузера руками** — бот работает через него.
Если закрыть, он это заметит, напишет в Telegram и остановится.

## Почему бот не хранит пароль

Логин и пароль нигде не хранятся и не вводятся программно. Причины две:

1. Вход всё равно подтверждается кодом из SMS или пуша — полностью
   автоматический вход невозможен в принципе. Хранение пароля добавило бы риск,
   не дав ничего взамен.
2. Если бот переедет на VPS, на чужой машине не будет лежать ничего, чем можно
   увести счёт — только профиль браузера с сессией, который банк в любой момент
   гасит сам.

Вход делает человек, один раз, в видимом окне. Дальше сессия живёт в профиле, а
бот замечает, когда она умерла, и просит зайти снова.

## Перевод себе (`/pay`)

Бот умеет готовить перевод себе в другой банк по СБП. Полностью автоматическим
он не сделан намеренно: последнее нажатие всегда за человеком.

1. `/pay 5000` (или кнопка «💸 Перевести себе в другой банк» в меню — тогда бот
   спросит сумму) — бот открывает форму, заполняет её и жмёт «Продолжить».
   Деньги пока на месте: банк показывает экран сверки;
2. бот присылает запрос на перевод с кнопками «✅ Подтвердить» и «✖️ Отменить»;
3. вы нажимаете «Подтвердить» — бот жмёт финальную кнопку;
4. если банк запросит код из SMS, бот попросит прислать его сообщением;
   на переводе себе ВТБ кода обычно не спрашивает;
5. бот читает со страницы исход и отвечает «✅ Отправлено».

Исход определяется по элементу, а не по тексту: кнопка «Получить чек» на экране
статуса бывает только у проведённого перевода, а формулировки банк меняет когда
захочет (`success`/`failure` в `transfer.json`; `success_text`/`failure_text`
остались запасным вариантом). Признак отказа проверяется первым — принять отказ
за успех хуже, чем наоборот.

**Почему подтверждение в чате, а не только код из SMS.** Изначально роль
предохранителя играл код: без человека перевод не уйдёт. Оказалось, что перевод
себе ВТБ проводит **без кода** — на экране сверки одна кнопка «Перевести» и
больше ничего. Останься схема прежней, `/pay` двигал бы деньги в одиночку.
Поэтому явное «да» в чате занимает место, которое раньше занимал код, и шаг 3
остаётся единственной точкой невозврата.

### Безопасность

- **Получатель зафиксирован в `.env`** (`TRANSFER_PHONE`, `TRANSFER_BANK`),
  а не берётся из чата. Даже с доступом к боту деньги не увести никуда, кроме
  этого счёта — из команды приходит только сумма.
- **Лимит суммы** (`TRANSFER_MAX_AMOUNT`) обязателен.
- **Черновой режим по умолчанию** (`TRANSFER_ARMED=false`): бот заполняет форму
  и останавливается, не нажимая даже «Продолжить». Видно, что он ввёл, но ничего
  не отправляется. Так подгоняется `transfer.json` — без единого случайного
  перевода. Реальная отправка включается `TRANSFER_ARMED=true` **в `.env`**
  (переменная окружения тоже подойдёт, она приоритетнее файла).
- **Подтверждение в чате перед финальной кнопкой** — и в боевом режиме тоже.
  Подтверждение — только кнопкой под запросом: текстом его дать нельзя, чтобы
  случайное сообщение в чат не сдвинуло деньги. Если кнопку не нажали, перевод
  истекает по `TRANSFER_OTP_WAIT` сам, ничего не нажав.
- **Отмена честно называет состояние**: до финальной кнопки `/cancel` пишет,
  что деньги на месте; после неё — что нажатие уже состоялось и надо смотреть
  историю. Бот не делает вид, что отменил то, что отменить не может.

### Как настроить

1. В `.env` задайте `TRANSFER_PHONE`, `TRANSFER_BANK`, `TRANSFER_MAX_AMOUNT`.
2. Скопируйте `transfer.example.json` в `transfer.json` и подгоните шаги под
   свою форму перевода. Поля ищутся по `testid`, роли, подписи, плейсхолдеру
   или тексту; значения подставляются через `{amount}`, `{phone}`, `{bank}`.
3. Дойдя в браузере до нужного экрана, снимите его командой **`/inspect`** —
   бот выведет поля и кнопки страницы с их селекторами (в чат — сводку, в
   терминал — полный список). Берите оттуда `testid`: он не зависит от текста
   и переживает косметические правки вёрстки.
4. Гоняйте `/pay` в черновом режиме, пока форма не заполняется правильно.
   Кнопку отправки бот не нажимает, но проверяет, что она найдена и активна,
   и пишет об этом в ответе — иначе её селектор впервые проверился бы на
   боевом переводе.
5. Только потом — `TRANSFER_ARMED=true`. Если при этом в `transfer.json` не
   описаны `submit` и `confirm`, бот откажется вооружаться и останется в
   черновом режиме, назвав недостающие шаги. Шаги `otp_field`/`otp_confirm`
   необязательны: если банк кода не просит, оставьте их пустыми.

Экран подтверждения (поле кода из SMS) в черновом режиме не открывается —
банк не доходит до него, пока ничего не отправлено. Его селекторы снимаются
`/inspect`-ом уже на первом боевом переводе.

#### Если шаг падает на поле, которого «нет» на странице

Первое подозрение — **написание тестового атрибута**. Playwright сам по себе
знает только `data-testid`, а ВТБ подписывает элементы `data-test-id`: поиск не
находил поле, которое `/inspect` тут же показывал на странице. Поэтому в шаге
достаточно написать `"testid": "sum_input"` — код проверяет все
распространённые написания (`data-testid`, `data-test-id`, `data-test`,
`data-qa`, `data-qa-id`, `testid`) и `id`. В снимке `/inspect` рядом с
идентификатором указано, каким атрибутом подписан конкретный элемент.
Если шаг всё же упал, к ошибке приложен ответ на главный вопрос: элемента на
странице нет вовсе, или он есть (и тогда дело в ожидании, а не в поиске) —
проверяются в том числе фреймы.

Второе подозрение — кастомное поле: настоящий `<input>` скрыт
(`visibility:hidden`), а видимую часть рисует `div` поверх. В снимке `/inspect`
такие поля помечены `[скрыто, ввод через fill работает]` — ждать их
«видимости» бессмысленно, но ввод по ним проходит: шаг `fill` пробует три
способа подряд (обычный ввод, набор с клавиатуры, прямая запись значения) и
после каждого перечитывает поле, сверяя число, а не строку — `5 000,00 ₽`
считается за `5000`.

### Риск

Читающий бот антифрод почти не трогает. **Автоматизированный исходящий перевод —
ровно тот паттерн, который F6 (экс-Group-IB) на сайте ВТБ ловит первым делом:**
форму, заполненную скриптом, видно по таймингам и отсутствию движений мыши.
Реальный исход при регулярном использовании — блокировка входа. Это ваш риск
и ваша ответственность.

**Штатная альтернатива без риска:** в приложении ВТБ есть регулярный автоперевод
по СБП себе в другой банк. Настраивается один раз, работает сам, без парсера.
Если нужен именно перевод фиксированной суммы по расписанию — используйте его.

## Риски

- Пользовательское соглашение банка, как правило, запрещает автоматизированный
  доступ к кабинету. Это ваше решение и ваша ответственность.
- Антифрод может потребовать переподтверждения входа или заблокировать доступ.
- Слишком частый опрос заметен. `POLL_INTERVAL=60s` — разумный минимум,
  меньше 15s код не даст выставить.
- Зеркала ВТБ живут недолго. Когда домен отвалится, поменяйте `BANK_HOST`.

## Структура

```
cmd/bot/           основной процесс
cmd/recorder/      разовый discovery ручек банка
cmd/mapper/        повторный разбор снятых дампов
cmd/doctor/        проверка окружения без захода в банк
internal/config/   конфиг из .env и окружения
internal/bank/     браузер, сессия, клиент API, поиск зеркал, recorder
internal/discover/ эвристики: какой массив — счета, какой — операции
internal/store/    SQLite
internal/poller/   опрос и поиск новых зачислений
internal/tg/       команды и уведомления
```

## Что автоматизировано, а что нет

Автоматически: поиск живого зеркала, поиск ручек банка, определение полей в
ответе, источник токена, генерация `endpoints.json`, слежение за операциями.

Руками — только вход в банк. Он подтверждается кодом из SMS или пуша, и это
не обходится ничем: не «сложно», а невозможно по устройству самой схемы.
Делается один раз, дальше сессия живёт в профиле браузера.
